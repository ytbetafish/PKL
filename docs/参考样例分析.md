# 参考样例分析：PCL-Deepseek-Harness-Launcher

## 文件
`D:\Downloads\PCL-Deepseek-Harness-Launcher.exe`（5.16 MB，.NET/WPF 单文件自包含 exe）

## 它删了什么 / 保留了什么
**它几乎没删 PCL 的任何 MC 模块**——反射字符串里仍然包含完整的 MC Mod 名列表（Forge/Fabric/NeoForge 几百个 Mod 标题）、`{java}java.exe -jar`、Fabric/NeoForge 图标、`PageDownload` 系列页面。也就是说这个二次开发样例**没有做 MC 剥离**，它是在 PCL-CE 完整 MC 启动器之上**追加**了一个 DeepSeek 集成页。

## 它怎么挂第三方 HTTP API
从字符串 dump 出的关键证据：
- Base URL：`https://api.deepseek.com`
- 模型：`deepseek-chat`
- 命名空间：`clr-namespace:PCL;assembly=PCL-Deepseek-Harness-Launcher`
- 新增页面：`PageDownloadHarness`（在 `PageDownloadHarness_Loaded` 里初始化，带 `IsFirstLoaded` 标志）
- 设置页：复用 `PageSetupSystem`（在 `PageSetupSystem_Loaded` 里初始化）
- 项目主页：`https://github.com/Loliyer520/DSHL-Deepseek-Harness-Launcher`

## 对我们 ITranslationService 设计的借鉴
1. **设置项挂载点**：它把 API 配置（base_url/key/model）放在 PCL 原有的 `PageSetupSystem` 设置页里，而不是新建独立设置窗口。我们也应该把 `TranslationOptions`（BaseUrl/ApiKey/Model）挂到现有设置 JSON / 设置页，而不是另起炉灶。
2. **调用层放在业务页面 code-behind**：`PageDownloadHarness_Loaded` 直接发请求，没有抽象成独立 Service。我们抽成 `ITranslationService` 是更干净的做法，但挂载位置相同——在需要翻译的页面 code-behind 里 `await TranslationService.TranslateAsync(text, "zh-CN")`。
3. **OpenAI 兼容协议**：它直接硬编码 `https://api.deepseek.com` + `deepseek-chat`，用的就是 `/chat/completions`。我们的 `OpenAiTranslationService` 与之一致，但把 base_url/key/model 做成 `TranslationOptions` 可配置，比它更灵活。
4. **它没有做的**：没有剥离 MC、没有抽 Service、没有做缓存。我们的剥离是它没做的工作。
